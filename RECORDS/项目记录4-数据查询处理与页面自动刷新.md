# 项目四：数据查询、处理与页面自动刷新

## 项目背景

第四个项目依旧是从数据库中查询数据，经过简单处理之后返回给前端进行展示。

经历了项目二的完整链路训练之后，这一次再接触类似需求时，我已经能够比较轻松地理解这个项目到底需要我做什么，也开始能大致判断数据会经过哪些文件、哪些层级，以及最终是怎么展示到页面上的。

不过，距离我最终“完全不依赖 Codex，自己手写所有代码”的目标还有很长一段路要走。

目前对我来说，最大的难点已经不只是代码本身，而是公司的业务逻辑。很多时候需要先理解一个页面展示的内容到底代表什么，再弄清楚数据库中的哪个表、哪个字段与它对应。这部分需要通过长期参与项目慢慢积累，不可能短时间内全部掌握。

因此，这一次项目给自己定下的目标并不是强行要求所有代码都自己写，而是：

> **尽可能看懂 Codex 帮我写出的代码，并且理解每一处修改为什么这样做。**

---

## 一、主动梳理前后端数据查询链路

项目开始后，我首先让 Codex 帮我分析：

**前端页面中的某一个数据，到底是怎样从后端查询并返回过来的？**

但这一次我没有只是让 Codex 直接告诉我答案，而是让它给出一个可以让我自己手动查看代码的顺序。

例如按照类似下面的思路去寻找：

1. 先找到前端页面展示数据的位置；
2. 找到前端调用的接口；
3. 根据接口地址找到对应的 Controller；
4. 再继续向下查看 Service；
5. 找到对应的 Mapper；
6. 最后定位到实际执行的 SQL；
7. 根据 SQL 确认数据库表和字段；
8. 再反过来理解数据是怎样一路返回到前端页面的。

通过这种方式，我开始能够自己顺着代码去寻找完整的数据调用路径。

虽然现在还不能完全脱离 Codex 独立定位所有代码，但相比之前完全不知道前端和后端之间是怎么联系起来的，已经有了非常明显的进步。

---

## 二、开始理解并手动修改 SQL

在 Codex 的辅助下，我这一次自己动手修改了项目中的 SQL 语句。

相比之前只是看到 SQL 就觉得比较陌生，现在已经开始能够理解：

- 查询的是哪个表；
- 需要拿哪些字段；
- 查询条件为什么这样写；
- 数据之间是通过什么条件关联的；
- 修改某一个字段之后，会对最终查询结果产生什么影响。

虽然 SQL 的修改过程依然有 Codex 帮助，但是我已经不再只是直接复制它生成的代码，而是开始尝试理解查询逻辑，并根据实际需求手动调整 SQL。

这对我来说是一个很重要的进步。

---

## 三、修改页面数据刷新逻辑

这一次项目中还修改了整个页面的数据刷新逻辑。

原本页面中的实时数据需要重新进入页面或者进行其他操作后才能获得最新结果。

为了让数据能够自动更新，我把接口调用增加了轮询机制：

> **每隔 1 小时自动请求一次后端接口。**

这样页面中的实时数据就能够每小时自动重新查询并刷新一次。

通过这个修改，我对“前端请求后端接口”这件事也有了进一步理解。

以前我只知道页面会向后端请求数据，现在开始理解：

- 页面什么时候调用接口；
- 接口是不是只能调用一次；
- 如何让接口按照固定时间重复调用；
- 后端数据更新以后，前端如何重新获取最新结果。

虽然只是一个简单的定时轮询功能，但对我来说也是第一次真正参与修改页面的数据刷新机制。

---

## 四、根据页面数据反查数据库字段

项目中还有一个很实际的问题：

**页面上显示的这个数据，到底对应数据库中的哪个字段？**

由于目前对公司的数据库表结构和业务字段还不熟悉，所以这部分我依然大量借助了 Codex。

我的处理方式是：

1. 先让 Codex 帮我找到当前页面数据最终来源于哪个表、哪个字段；
2. 再根据实际业务需求确定我真正想展示的数据；
3. 告诉 Codex我要对应的字段含义；
4. 让它根据现有代码和数据库结构帮我完成字段对应和修改。

这种方式虽然还比较依赖 AI，但至少我已经开始理解：

> **页面上的一个数据并不是凭空出现的，而是可以一路从前端代码追踪到后端接口，再追踪到 SQL，最后找到数据库中的具体字段。**

这也是我目前非常需要建立起来的一种开发思维。

---

## 五、这次项目相比之前的进步

经历项目二之后，再做这一次类似的数据查询项目，我已经能明显感觉到自己的变化。

### 以前

看到需求之后，我甚至不知道：

- 应该先找前端还是后端；
- Controller 是什么；
- Service 是干什么的；
- Mapper 在哪里；
- SQL 和页面的数据有什么关系；
- 前端究竟是怎么拿到数据库中的数据的。

### 现在

虽然还无法完全独立完成，但至少已经能够：

- 理解项目大概要做什么；
- 顺着前端接口寻找后端代码；
- 大致看懂 Controller → Service → Mapper → SQL 的调用关系；
- 在辅助下修改 SQL；
- 根据需求寻找数据库中的字段；
- 修改页面的数据刷新逻辑；
- 理解接口轮询的作用；
- 借助 Codex 完成代码，同时尽量看懂它为什么这样写。

从“完全不知道整条链路怎么运行”，到现在已经能够主动沿着调用链去阅读和修改项目，说明之前做项目积累下来的经验确实开始发挥作用了。

---

## 六、目前仍然存在的问题

现在离“完全自己写代码”还有很远。

目前比较明显的问题主要有两个。

### 1. 对业务和数据库结构不熟悉

公司的系统已经存在大量数据库表和业务字段。

很多代码问题实际上并不是 Java 语法问题，而是：

> **我不知道业务上的这个数据，在数据库中到底叫什么、存在哪里、和哪些表有关。**

这一部分只能通过长期参与项目慢慢熟悉。

---

### 2. Mapper 和 SQL 还不能完全独立完成

目前我虽然已经能够在 Codex 的帮助下找到 Mapper 和 SQL，并进行修改，但是还做不到：

- 完全自己找到应该修改哪个 Mapper；
- 完全自己判断 SQL 应该怎样设计；
- 独立完成查询逻辑；
- 熟练理解 Mapper、Service、Controller 之间的关系；
- 不依赖 AI 完成整条后端开发流程。

这部分需要继续补充 Java Web 和 Spring Boot 的系统知识。

---

## 七、下一阶段目标

现在不需要着急要求自己马上完全脱离 Codex。

现阶段更重要的是：

> **每一次让 Codex 写完代码之后，都尽可能弄懂这段代码到底在干什么。**

接下来继续补基础知识，尤其是：

- Java 基础语法；
- SQL；
- MyBatis / Mapper；
- Spring Boot；
- Controller；
- Service；
- 前后端接口调用；
- HTTP 请求；
- 数据库表之间的关系；
- 公司现有项目的业务逻辑。

等系统学习到 Spring Boot 之后，希望能够真正做到：

> **自己找到 Mapper → 自己写 SQL → 自己写 Service 处理逻辑 → 自己写 Controller → 自己完成前端接口调用。**

最终目标依旧没有变化：

**不只是能够让 AI 把功能做出来，而是自己能够完全看懂代码，并且最终能够亲手把整套代码敲出来。**

---

## 项目总结

第四个项目本身的逻辑依然不复杂，但相比功能本身，我更在意的是自己理解项目的方式正在发生变化。

以前面对一个新需求，我只能问：

> “这个功能应该怎么写？”

现在我已经开始问：

> “这个数据从哪里来的？”  
> “我应该按照什么顺序去找代码？”  
> “前端调用的是哪个接口？”  
> “这个接口对应哪个 Controller？”  
> “SQL 在哪里？”  
> “页面这个数据对应数据库哪个字段？”  
> “为什么这里要这样写？”

这说明我已经开始从单纯“让 Codex 帮我完成需求”，逐渐向“借助 Codex 学会理解一个真实项目”转变。

现在依旧很依赖 Codex，没有关系。

先做到 **看懂**，再做到 **能改**，然后做到 **能模仿着写**，最后再做到 **完全独立写出来**。

慢慢学，一点一点把这些能力变成自己的。
