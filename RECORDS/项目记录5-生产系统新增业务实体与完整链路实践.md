# 项目五：生产系统新增业务实体与完整前后端链路实践

## 一、项目背景

第五个项目相比之前几个项目又向前迈了一大步。

这一次不再只是从数据库中查询已有数据并简单处理后展示，而是需要直接在公司的生产系统中新增一套完整业务功能，涉及：

- 数据库
- 后端
- 前端
- 业务计算逻辑
- 页面交互
- 数据保存与返回

项目的核心业务是：

> 根据油漆使用量，按照生产部门提供的配比公式计算出对应需要添加的固化剂数量。

除此之外，还需要考虑实际固化剂添加量与标准值之间的偏差：

- 加多了如何处理
- 加少了如何处理
- 不同情况需要进行不同的后续逻辑判断

这已经不再只是一个简单的数据查询需求，而是真正开始接触一个完整业务功能从数据库到页面的实现过程。

## 二、这次对前后端结构有了更加清晰的认识

通过这个项目，我第一次比较完整地理解了公司项目中一个页面的数据和操作是如何一步一步传递到后端的。

以前我经常看到很多 Vue、JavaScript、Controller、Service、Mapper、XML 文件混在一起，很难理解它们之间到底是什么关系。

这一次，我逐渐把整条链路串联了起来。

整体调用关系大致可以理解为：

```text
工人使用的 Vue 页面
        ↓
前端 JavaScript 接口/API 文件
        ↓
HTTP 请求
        ↓
Controller
        ↓
Service 接口
        ↓
ServiceImpl 实现类
        ↓
Mapper 接口
        ↓
Mapper.xml
        ↓
数据库
```

这也是这次项目带给我最大的收获之一。

## 三、重新理解 Vue 页面和 JavaScript 请求文件

一开始我把项目中的两个前端文件理解成了“两个前端页面”。

后来进一步理解后发现，这种说法并不准确。

真正给工人操作和查看的是 Vue 页面。

例如页面负责：

- 输入油漆数量
- 点击按钮
- 展示计算结果
- 展示固化剂数量
- 显示业务状态

而另外一个 JavaScript 文件并不是另一个真正给用户看的页面。

它更像是一个专门负责“前端和后端通信”的接口文件。

它通常会负责：

- 请求哪个接口
- 请求地址是什么
- 使用 GET 还是 POST
- 传递哪些参数
- 如何通过 axios 或项目封装好的 request 方法发送 HTTP 请求

因此，现在我对前端的理解变成了：

> Vue 页面主要负责“人看到什么、点击什么”，JavaScript 接口文件主要负责“页面怎么向后端发请求”。

这个理解让我第一次真正意识到：

**前端页面代码和前端接口请求代码同样可以进行分层。**

## 四、终于理解为什么 Service 会有两个文件

这次项目中，我发现 Service 相关代码并不是只有一个文件。

以前我一直误以为：

> 一个 Service 文件里面应该负责所有业务运算逻辑。

所以以前阅读公司项目时，经常会觉得代码很奇怪。

有时候打开一个 Service 文件，只看到几个方法声明，却完全看不到真正的业务代码，因此经常不知道真正的计算逻辑到底去了哪里。

这次终于理解了：

通常会存在：

```text
XXXService.java
```

和：

```text
XXXServiceImpl.java
```

两个文件。

它们负责的事情并不一样。

### Service 接口

Service 接口主要负责声明：

> 这个业务层“能做什么”。

例如：

```java
BigDecimal calculateHardener(...);
```

这里只声明存在这样一个方法，但并不真正编写具体的计算过程。

### ServiceImpl 实现类

真正的业务逻辑一般写在：

```text
XXXServiceImpl.java
```

里面。

也就是：

> Service 定义方法，ServiceImpl 负责把方法真正实现出来。

这种“接口 + 实现类”的结构，是 Java 项目中非常常见的一种设计方式。

我以前看不懂 Service，很大程度上就是因为不知道：

**方法声明和方法实现可以分别存在于两个文件中。**

现在理解之后，再回头看公司的项目结构，就会感觉清晰很多。

而且这种写法确实比把所有内容都堆在一个文件里面更加简洁，也更容易维护。

## 五、Mapper 和 SQL 也存在类似的结构

Mapper 这一层也让我进一步加深了理解。

在我们公司的项目中，Mapper 同样不是直接把所有 SQL 都写在 Java 文件里。

通常会分成：

```text
XXXMapper.java
```

和：

```text
XXXMapper.xml
```

Mapper.java 主要负责声明数据库操作方法。

例如：

```java
PaintInfo selectPaintInfo(Long id);
```

真正执行的 SQL 则写在 Mapper.xml 中。

例如：

```xml
<select id="selectPaintInfo">
    SELECT ...
    FROM ...
    WHERE ...
</select>
```

所以现在我对 Mapper 的理解是：

> Mapper.java 主要负责声明“要做什么数据库操作”，Mapper.xml 才负责写“具体应该执行什么 SQL”。

这个模式和 Service 非常类似：

```text
Service         → 声明业务方法
ServiceImpl     → 实现业务方法

Mapper          → 声明数据库方法
Mapper.xml      → 编写真正 SQL
```

理解这一点以后，我再去阅读项目代码时，会开始主动寻找：

- 方法在哪里声明
- 方法在哪里实现
- SQL 在哪里真正编写

而不是看到一个文件里没有完整逻辑就觉得代码“断掉了”。

## 六、Controller 的作用也开始变得更加清晰

经过这几个项目后，我也越来越能理解 Controller 在整个系统中的位置。

Controller 本身一般不会负责大量复杂的业务运算。

它更像整个后端的“入口”。

前端发送 HTTP 请求后：

```text
前端
 ↓
Controller
```

Controller 接收到请求参数，然后调用 Service 中已经定义好的业务方法：

```text
Controller
 ↓
Service
```

Service 再继续进行真正的业务计算、判断或数据库查询。

完成之后：

```text
Service
 ↓
Controller
 ↓
前端
```

最后由 Controller 把处理结果返回给前端。

因此，现在我逐渐形成了这样一个理解：

> Controller 负责接收请求和返回结果，Service 负责业务逻辑，Mapper 负责数据库操作。

虽然目前还无法完全独立写出这些代码，但至少整个分层结构已经开始逐渐清晰。

## 七、第一次真正注意到 BigDecimal

这次项目中还有一个非常重要的新知识点：

**BigDecimal。**

油漆和固化剂之间需要按照生产部门给出的配比公式进行计算。

一开始我以为这种计算就是普通的：

```text
+  -  *  /
```

后来发现项目中的核心计算并不是直接使用普通数字运算，而是使用了 Java 中的：

```text
BigDecimal
```

需要特别注意的是：

**BigDecimal 不是一个函数，而是 Java 中专门用于高精度十进制计算的一个类。**

它进行加减乘除时通常会使用：

```java
add()
subtract()
multiply()
divide()
```

例如除法可能类似：

```java
paintAmount.divide(ratio)
```

而不是直接使用：

```java
paintAmount / ratio
```

---

## 八、为什么工业生产计算要使用 BigDecimal

BigDecimal 的意义并不只是：

> `.divide()` 比 `/` 更精确。

更准确地说：

> BigDecimal 可以进行可控的高精度十进制运算，避免 float 和 double 可能出现的浮点误差。

在下面这些场景中：

- 金额
- 重量
- 配比
- 油漆用量
- 固化剂用量
- 工业生产参数

计算精度往往非常重要。

所以，在生产系统中使用 BigDecimal 进行配比计算是非常合理的。

以后还需要继续学习 BigDecimal 中非常重要的一部分：

```java
divide(除数, 小数位数, 舍入规则)
```

例如：

```java
a.divide(b, 2, RoundingMode.HALF_UP)
```

这代表：

- 除以 b
- 保留两位小数
- 使用指定的舍入方式

BigDecimal 是我以后必须认真补充的 Java 基础知识之一。
